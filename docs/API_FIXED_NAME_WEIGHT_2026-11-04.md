# M03 음식명 고정 API 중량 재실험 (2026-11-04)

## 목적

M02(같은 AR 실측 11건 API 중량 비교)에서 오차 중 음식명 오인식 때문인 부분을 빼고, API(gpt-4o-mini)의 **순수 중량 추정 정확도**를 확인한다. M05에서 "분류 모델로 확정한 음식명을 API 중량 요청에 전달"하는 구조의 근거가 된다.

## 방법

- 요청 본문: M02에서 사용한 `data/private/ar/api-compare-requests/*.json`을 그대로 사용(같은 사진·서버 지시문·스키마·AR 깊이 요약·모델). 작업 문장 바로 뒤에 아래 한 문단만 추가했다.
  > 사용자가 확인한 음식명: {음식명}. 사진 속 대상 음식은 이 한 가지입니다. items는 1개만 반환하고 name은 '{음식명}'로 그대로 쓰세요. 음식 종류를 다시 판단하지 말고, 사진과 측정 근거로 이 음식의 실제 보이는 양에 대한 grams·weightEstimate·assumptions만 추정하세요.
- 11건 × (사진만 / 깊이 포함) × 3회 = 66회 호출. 실패 0회, null 중량 0회, 총 토큰 약 99.8만.
- 도구: `scripts/compare_api_weight_fixed_name.py` (`run` → `score`). 원자료: `data/private/ar/api-compare-fixed-name/` (`responses/`, `summary.json`).
- 오차: 3회 중앙값과 저울값의 상대오차.

- 깊이 요약을 넣어도 일관되게 좋아지지 않았다(중앙값은 오히려 높음).

## 원인

응답의 가정(assumptions)이 오차 방향을 설명한다. 모델이 보이는 양을 측정하지 않고 **일반적인 1회 제공량**을 기준으로 답한다.

- 밥-A(13g) → 150g: "밥 한 그릇의 평균 양", "대략 1인분으로 추정"
- 밥-B(13g) → 100g: 불확실성에 "밥의 양은 비교적 적은 편"이라고 쓰고도 "일반적인 식사 제공량을 기반"으로 100g
- 커피땅콩-A(12g) → 150g: "커피땅콩 1인분의 평균적인 양을 기준"

음식명을 알려 주면 그 음식의 "보통 1인분"이 더 분명해져, 소량 기록(밥-B·C)에서는 오히려 과대 추정이 커지기도 했다. 맞은 기록(쿠키-C, 커피땅콩-D·E·F)은 실제 양이 일반 간식량 근처(24~55g)인 경우다.

## 한계

- 11건, 3개 음식, 12~55g 소량만 대상이다. 실제 1인분(150~300g) 식사는 시험하지 않았으므로, 일반 식사에서는 "보통 1인분" 기준이 우연히 맞을 수 있다. 이 결과는 **보통 양에서 벗어난 양을 API가 읽지 못한다**는 근거이며, 일반 식사의 오차 크기를 말해 주지는 않는다.
- 모델은 gpt-4o-mini 하나, 프롬프트는 서버 지시문 + 고정 문단 하나다. 다른 모델이나 크기 기준(접시 지름·손·카드) 프롬프트는 시험하지 않았다.

## 결론과 반영

1. **인식 오류를 없애도 API 중량은 측정값으로 쓸 수 없다.** M02의 큰 오차는 오인식보다 "1인분 기준 추정"이 주된 원인이다.
2. **M05(인식 개편):** 확정 음식명을 API에 전달하는 것은 음식명·영양 DB 매칭에는 유효하지만, 중량 정확도를 높이는 수단으로 기대하지 않는다.
3. **M06(중량 개편):** API 중량은 "일반 1회 제공량 기본값"으로 표시하고 사용자 수정을 전제로 한다. 범위의 저울값 포함률이 21%이므로 범위를 신뢰구간처럼 표시하지 않는다. 품질 조건을 통과한 AR 부피식이나 사용자가 입력한 중량을 API보다 우선한다.
4. 후속 후보(미실행): 일반 1인분 크기 식사로 같은 비교, 크기 기준 물체를 넣은 프롬프트, 상위 모델 비교.
