# Gemma 음식 인식 저하 원인 분석 2026-11-02

## 확인한 사실
- 50개 서로 다른 분류의 주 음식명 일치: Gemma 8/50(16%), API 29/50(58%). 같은 모델·같은 프롬프트의 순수 비교가 아니라 현재 구성끼리의 탐색 비교다.
- Gemma 정상 응답 48건, JSON/필수 구조 검증 실패 2건(후무스·팬케이크). 정상 응답만의 일치율도 8/48=16.67%로, 형식 오류를 모두 고쳐도 현재 평가에서 최대 10/50=20%다. 형식 오류만으로 격차를 설명할 수 없다.
- 넓은 분류 출력이 많다. 브루스케타→토스트, 미소국→수프/스튜, 당근 케이크→케이크, 팟타이→볶음면. 평가에서는 구체 분류를 맞혀야 하므로 이런 결과도 미일치로 처리했다. 상위 분류 정확도는 별도로 재채점하지 않았다.
- 고기·디저트 등 실제 오인식도 존재한다. 핫도그→햄버거, 바클라바→갈비찜, 크렘 브륄레→커피. 단순 음식명 표기 차이로만 설명하기 어렵다.
- 전송한 50개 파일의 SHA256 원본 일치를 확인한 정상 평가 결과를 사용했다. 앞선 파일 전송 실패 실행은 제외했다.
- 사진별 새 conversation을 만들며 엔진만 재사용한다. 새 엔진 재검증에서도 크렘 브륄레→커피, 베니에→음식, 햄버거→햄버거가 재현되었다.

## 추가 PC CPU 대조
동일 LiteRT 모델 파일과 같은 음식명 한국어 프롬프트를 CPU에서 실행했다.
- 크렘 브륄레: 커피. 39.466초, 정상 JSON.
- 라멘: 수프 또는 국물 요리 등. 52.671초, 정상 JSON.
Android GPU 결과와 비슷한 오류가 재현되어 GPU만의 문제라는 설명은 지지되지 않는다. PC Python 런타임 0.18.1과 Android 0.16.1, JPEG quality90/85 등 조건 차이가 있어 GPU 영향 전체를 배제한 통제 실험은 아니다.

## 코드에서 확인한 제약과 아직 검증할 가설
- 사전학습 Gemma 4 E2B에 음식 분류 전용 추가 학습이나 검색 후보를 적용하지 않았다. Google 문서에서 E2B는 모바일·엣지용 소형 범용 모델이다. 특정 음식 지식·구분 성능이 낮을 가능성이 있지만, 모델 규모만을 원인으로 확정할 비교 실험은 아직 없다.
- 프롬프트는 한국어로 모든 음식을 나열하고 JSON을 출력하도록 한다. 구체적인 메뉴명 수준·예시·후보가 없고 불확실하면 알 수 없는 음식으로 답하도록 한다. 한국어/영어, 주 음식 하나/모든 음식, 자유 출력/JSON, 동일 프롬프트 API 비교로 부담과 언어 영향을 분리할 수 있다.
- Android는 긴 변 512px, JPEG85, 최대 출력 256토큰, thinking 비활성이다. 미세한 재료·토핑 손실, 출력 제한, 추론 설정이 영향을 줄 수 있지만 각각의 원인 효과는 실측 전이다. 256토큰이 두 형식 오류의 직접 원인인지는 원시 실패 응답을 보존하지 않아 현재 확정할 수 없다.
- Food-101 분류당 1장이고 서양 음식 비중이 높다. 사진·라벨의 모호성, 단일 검토자의 동등 표현 판정도 점수에 영향을 준다. 16%는 이 구성과 자료의 주 음식 분류 일치율이며 Gemma 모델 전체의 일반 정확도가 아니다.
- 양자화·GPU 수치 정밀도·발열을 주원인으로 단정할 근거는 확보되지 않았다.
