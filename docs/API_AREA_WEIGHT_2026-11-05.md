# API 중량 추정에 AR 실측 크기 제공 (M12, 2026-11-05)

## 목적
AR이 픽셀 깊이로 음식 높이를 재는 방식은 촬영 조건(무광 접시, 높이 있는 음식, 긴 촬영)이 까다롭다. 그래서 AR은 **실제 크기(축척·면적)만 측정**하고 중량은 API가 직접 추정하게 하는 구조(A안)를 검토했다. 확인할 질문은 두 가지다.
1. 실제 크기를 근거로 주면 API가 "보통 1인분" 대신 보이는 양으로 중량을 추정하는가?
2. 음식 윤곽(면적)이 꼭 필요한가? 축척만 주는 경우와 비교한다.

## 방법
- 대상: 저울값이 있는 AR 기록 11건 중 10건. 밥-B는 모든 프레임의 깊이가 2~16m로 깨져 있어 제외했다.
- 기준선: M03의 음식명 고정·사진만 결과([API_FIXED_NAME_WEIGHT_2026-11-04.md](API_FIXED_NAME_WEIGHT_2026-11-04.md))
- 조건: 사진, 고정 음식명, 프롬프트는 M03과 같고 근거 문장 하나만 추가했다.
  - **축척만**: 접시 면까지의 거리, 1픽셀당 mm, 사진 전체의 실제 가로×세로(cm)
  - **축척 + 면적**: 위 축척에 더해, 검수한 수동 윤곽으로 계산한 위에서 본 음식 면적(cm²)
  - 두 조건 모두 "1인분을 기준으로 삼지 말고 보이는 크기·두께·개수로 계산하라"고 지시했다.
  - **높이만**(추가 실험): 축척과 면적을 주고 API에는 평균 높이(cm)만 물었다. 평균 높이 = 부피 ÷ 면적이고, 영역 안의 빈틈은 높이 0으로 친다. 중량은 스크립트가 **면적 × AI 높이 × 분류 밀도**로 계산했다. 밀도는 DensityGroups 값을 썼다(밥 0.73, 쿠키 BAKERY 0.42, 커피땅콩 NUT 0.63).
- 거리 계산:
  - 세션의 마지막 프레임(깊이가 수렴한 프레임)에서 접시 영역(음식 제외)의 깊이 중앙값을 썼다. ARCore 평면까지의 거리를 대신하는 값이다.
  - 첫 프레임은 깊이가 덜 수렴한 경우가 있었다(쿠키-C 첫 프레임 1083mm, 마지막 프레임 289mm).
- 면적 = 윤곽 다각형 면적(px) × (거리/fx)(거리/fy). 바로 위에서 찍었다고 가정했다.
- 모델: gpt-4o-mini, 조건별 3회, 상대오차는 3회 중앙값 기준. 총 90회 호출했다(중량 직접 60회, 높이만 30회).
- 스크립트: `scripts/compare_api_weight_area.py` (geometry / dry-run / run / score)
- 결과: `data/private/ar/api-compare-area/` (Git 제외)

## 해석
1. **실제 크기를 줘도 API 중량은 좋아지지 않았다.** 축척만 준 경우는 중앙값이 오히려 나빠졌고(111% → 192%), 면적까지 줘도 138%로 M03보다 낫지 않다. 반환값도 여전히 30·50·100·150처럼 둥근 숫자에 몰린다.
2. **API는 근거 수치를 계산에 제대로 쓰지 않는다.** 응답의 가정과 결과가 서로 맞지 않는다.
   - 밥-A(13g, 면적 7.7cm²): API는 "높이 3cm, 밀도 0.8"이라고 적었다. 이대로 계산하면 7.7×3×0.8 ≈ 18g인데 답은 100g이었다.
   - 쿠키-B(31g, 면적 40.4cm², 지름 약 7cm에 해당): API는 지름 10cm, 두께 2~3cm로 가정했다. 실제 쿠키 두께는 약 1cm다.
3. **음식 윤곽(면적)의 효과는 작고 일정하지 않다.** 축척만 준 경우와 비교하면 개선 3건(밥-A, 커피땅콩-C·F), 악화 2건(커피땅콩-D·E), 동일 5건이다. 중량을 직접 묻는 방식에서는 API가 면적을 거의 쓰지 않으므로, 윤곽이 있어도 결과가 크게 달라지지 않는다.

4. **높이만 묻고 곱셈을 따로 하면 크게 좋아졌다.** 중앙값이 111%에서 63%로, 평균이 290%에서 126%로 줄었다. 밥(15%)과 쿠키(34%)처럼 한 덩어리인 음식에서 효과가 컸다. API가 1인분 중량을 떠올릴 여지가 없어지고 산술 오류도 사라진 결과로 본다. 밥-A(13g)는 중량을 직접 물었을 때 100~150g이었지만, 이 방식에서는 8~20g이 나왔다.
5. **흩어진 음식(커피땅콩)은 오히려 나빠졌다(27% → 142%, 모두 과대).** 윤곽 안의 빈틈을 높이 0으로 치라고 지시했지만, API는 땅콩 한 알의 두께(1.5~2.9cm)를 그대로 답했다. 필요한 평균 높이는 0.3~0.8cm였다. 윤곽이 땅콩 사이 빈틈까지 감싸고 있어서 면적이 실제보다 크다.

## 결론
- **"면적을 주고 중량을 직접 묻는" 방식은 측정값으로 쓸 수 없다.** 근거를 줘도 API가 1인분 기준과 부정확한 산술에서 벗어나지 못한다.
- **"높이만 묻고 서버가 면적 × 높이 × 분류 밀도로 계산하는" 방식이 지금까지 시험한 방식 중 가장 정확하다.** 한 덩어리 음식에서 오차는 15~34% 수준이다.
- 윤곽이 필요한지는 중량을 묻는 방식에 따라 달라진다.
  - 중량을 직접 묻는 방식: 윤곽의 효과가 미미하다.
  - 높이 방식: 면적이 계산식에 직접 들어가므로 윤곽이 필수다. 윤곽의 품질이 곧 정확도다. 흩어진 음식에서는 덩어리 전체를 감싸는 윤곽이 빈틈을 포함해 크게 과대해진다.
- 남은 과제:
  1. 흩어진 음식은 조각별 윤곽의 합으로 면적을 구하거나, API에 덮인 비율(%)을 따로 묻는 방식을 검토한다.
  2. 이번 면적은 수동 윤곽으로 구한 것이다. 자동 윤곽(AI 위치 + 깊이 또는 AI 다각형)으로도 같은 정확도가 나오는지 확인해야 한다.
  3. 거리는 ARCore 평면 대신 깊이 중앙값으로 대신했다. 앱에서는 평면 인식이나 hit-test로 바꿔야 한다.

## 한계
- 10건, 3개 음식, 12~55g 소량이다. 일반 1인분 식사는 시험하지 않았다.
- 높이 방식의 밀도는 시험 음식의 의도한 분류값을 직접 넣었다. 앱처럼 DB 매칭을 거치면 분류가 틀릴 수 있다(예: '아몬드'가 빵 및 과자류로 매칭됨).
- 높이 응답 일부가 영어로 왔다(커피땅콩-F). 값에는 영향이 없다.
- 거리는 ARCore 평면 대신 수렴한 원시 깊이의 중앙값을 썼다. 접시 윤곽은 첫 프레임에서 그린 것이고, 거리는 마지막 프레임에서 잰 값이라 두 프레임 사이 카메라 이동 오차가 있다. 밥-A는 첫 프레임 거리(411mm)와 마지막 프레임 거리(594mm)가 크게 달라 면적의 불확실성이 크다.
- 면적은 수동 검수 윤곽으로 계산한 최선의 경우다. 자동 윤곽에서는 오차가 더 커질 수 있다.
