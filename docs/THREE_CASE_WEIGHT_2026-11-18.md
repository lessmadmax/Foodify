# 기존 자료의 중량 추정 세 조건 비교

## 목적과 현재 상태

사용자가 지정한 세 조건으로 비교를 완료하였다. 사용자의 명시 승인 후 저울 표시창을 가린 사진으로 유료 66회 호출을 실행했다. 통신·응답 JSON 파싱 오류는 0건이다. 그릇 기본 깊이와 이전 높이 4.29cm는 이번 API 입력에 포함하지 않았다.

## 핵심 결과

API는 각 사진의 성공한 반복 응답 3회 이하에서 중량 중앙값을 구한 뒤 표본 단위로 평가했다. 아래 확보율은 3회 중 대상 중량을 한 번이라도 확보한 표본의 비율이며 단일 호출 성공률이 아니다. 산술식은 한 번 재계산하였다.

| 조건 | 대상 중량 확보 | MAE(g) | 상대오차 중앙값 |
|---|---:|---:|---:|
| 사진만 API | 10/11 (90.9%) | 40.80 | 113.42% |
| 사진+AR 깊이 요약 API | 10/11 (90.9%) | 47.80 | 146.68% |
| 기기 측정+서버 산식 재현 | 4/11 (36.4%) | 25.85 | 72.47% |

오차는 각 조건에서 대상 중량을 확보한 표본만의 값이다. 따라서 산술식의 오차 수치가 작다는 이유만으로 가장 좋은 방식이라고 결론 내릴 수 없다. 세 조건 모두 수치를 확보한 공통 4건에서는 사진 API MAE 47.00g·상대오차 중앙값 70.77%, AR API 53.25g·100.98%, 산술식 25.85g·72.47%였다. MAE와 상대오차는 순위가 다를 수 있다.

API 단일 호출 기준 대상 중량 확보는 사진 27/33(81.8%), AR 29/33(87.9%)였다. API 자체는 66/66 응답했고, 중량 null과 대상 연결 불가를 확보 실패로 집계했다. 수치가 없는 조건에 오차 0을 부여하지 않았다.

사진/AR 모두 평가 가능한 10건 중 사진만의 절대오차가 작은 경우 6건, AR 추가가 작은 경우 1건, 동일 3건이었다. 이 작은 개발 자료에서는 AR 깊이 요약 추가에 따른 중량 오차 개선을 확인하지 못했고, 전체 오차 지표는 악화되었다. 이는 다른 품질의 AR 측정이나 전체 깊이 맵 활용에도 효과가 없다는 뜻은 아니다.

### 대상 매칭과 전처리 검토

원본 11장을 시각 확인하여 표시창이 보이는 6장(인덱스 0·1·2·8·9·10)에만 회색 직사각형을 적용했다. 나머지 5장은 표시 숫자가 보이지 않았다. 전송 사본은 PNG로 저장했고 가로·세로 640×480과 원래 좌표를 유지하였다. 두 API 조건은 같은 사본을 썼고 원본 SHA-256가 유지됨을 확인했다. 가림은 표시창에 한정했지만 일부 인덱스에서는 인접한 접시 가장자리 일부도 덮일 수 있다. 음식 본체는 보존했다.

음식명 오인식을 중량 null과 혼동하지 않도록 원본 응답 66개를 검토해 대상 항목을 매칭했다. 커피땅콩을 시리얼·그래놀라로 부르더라도 대상 접시의 항목으로 연결되는 경우 중량은 평가하고 이름 오류는 보존했다. 커피땅콩-A는 과자·요거트·음료·접시 포함 음식 등의 여러 항목이 생겨 실제 대상에 유일하게 연결하기 어려워 전 반복을 대상 미확보로 처리했다. 따라서 이 표는 음식명 정답률이 아니며 대상 매칭에는 사후 수동 판단이 포함된다. 반복별 원문과 항목 선택 근거는 `target-item-review.json` 및 `summary.json`에 남겼다.

### 호출량과 시간

모델 스냅샷은 `gpt-4o-mini-2024-07-18`, 입력 958,995토큰, 출력 10,511토큰이었다. 공식 단가로 캐시 할인 없이 계산한 추정액은 약 US$0.1502이며 실제 청구액 확인값은 아니다. 평균 API 응답 시간은 사진 약 4.24초, AR 약 4.00초다. 준비·전처리·앱 전체 흐름 시간은 포함하지 않는다. 승인된 66회만 실행했고 자동 재시도·추가 호출은 하지 않았다.

### 결론과 다음 검증

현재 자료의 장면 깊이 요약만 추가하는 방식은 채택 근거가 부족하다. 장면 중앙값은 음식 표면이나 접시 기준면을 특정하지 못하며, 기존 촬영의 깊이 품질과 카메라 기울기 문제도 남는다. 이후에는 음식·기준면에 대응하는 깊이와 면적을 검증된 좌표로 추출하는 조건을 별도로 시험해야 한다. 산술식은 실패 원인을 줄여 확보율을 높인 뒤 다시 비교해야 한다. 이번 개발용 11건을 독립 검증 성능으로 일반화하지 않는다. 앱의 중량 코드는 변경하지 않았다.

## 비교 조건

1. API에 사진만 제공하여 음식별 중량을 추정한다.
2. 같은 사진·모델·질문에 AR 깊이 자료만 추가하여 중량을 추정한다. 장면 깊이 중앙값, 유효 비율, 시간차, 카메라 내부 파라미터를 주되 음식 높이로 오인하지 않도록 정의한다. 깊이 불량 자료도 포함하고 사용 판단을 기록한다.
3. 기기에서 면적·높이를 얻고 서버 `MealService.areaHeightPreview`와 같은 면적×높이×분류 밀도·반올림 산식으로 계산한다. AI 높이 대체는 끄고 측정 불가를 실패로 남긴다. 기하 계산 재현과 서버 산술 계산을 구분하여 기록한다.

그릇 기본 깊이와 추가 음식 면적을 API 조건에 제공하는 별도 실험은 이번에 포함하지 않는다. 4.29cm·499.5g 등 이전 추정 결과도 API에 제공하지 않는다. 정답 음식명·중량은 평가용으로만 사용한다.

## 자료와 실행 범위

기존 저울값이 연결된 밥·쿠키·커피땅콩 11건, 조건 1·2 각각 3회로 최대 66회 호출한다. 조건 3은 동일 자료의 결정적 재계산이며 반복 호출하지 않는다. 최근 105g 사진은 이번 묶음에 추가하지 않는다. 11건은 과거 개발용 자료이며 독립 검증 자료가 아니다. 밥-B의 깊이 이상도 누락하지 않고 확보율에 반영한다.

같은 제공량의 반복 기록이 서로 독립인지 아직 검증하지 않았으므로 11개 독립 제공량이라고 표현하지 않는다. 원본 사진의 저울 숫자 노출은 실행 전 확인하고 위 전처리를 두 조건에 동일 적용하였다. 포장지·그릇·배경의 크기는 여전히 사진 속 크기 단서로 남는다.

입력 생성 스크립트 `scripts/compare_weight_three_cases.py`, 비공개 입력·응답 경로 `data/private/ar/three-cases-2026-11-18/`. `manifest.json`의 평가용 저울값은 요청에 들어가지 않으며 API에는 각 `requests` 객체만 전송한다. 원본은 수정하지 않는다.

서버 산술 경로는 현재 소스와 사용자 영역으로 재현해야 하며, 과거 깊이 적분 결과를 현 AREA_HEIGHT 결과로 대체하지 않는다. 오래된 자료에 특징점이 없으면 그 점을 임의로 생성하지 않는다. 원본 코드와 출처를 기록하고 앱 코드는 변경하지 않는다.

## 평가와 비용

### 로컬 산술 재계산 결과

현재 `ArFusion.combine`와 `ArVolume.scale`을 임시 Kotlin 재생 도구로 실행하고 `MealService`의 부피 0.1mL·중량 0.1g 반올림 및 최소값 규칙을 적용하였다. 필터 테스트 실행은 성공하였다. 앱 소스는 수정하지 않았고 임시 테스트는 제거했으며 원본과 소스 해시는 비공개 출력 폴더에 보존하였다. 실제 서버 HTTP 요청·DB 매칭 실행은 아니므로 그 단계의 성능을 포함하지 않는다.

| 자료 | 저울(g) | 산술 중량(g) |
|---|---:|---:|
| 밥-C | 51 | 24.8 |
| 커피땅콩-C | 27 | 4.9 |
| 커피땅콩-E | 24 | 3.6 |
| 커피땅콩-F | 55 | 20.3 |
| 나머지 7건 | 각 기록 참조 | 확보 실패 |

결과 확보 4/11(36.4%), 성공 4건 MAE 25.85g, 상대오차 중앙값 72.47%다. 실패는 오차 평균에서 빠지므로 확보율을 반드시 함께 읽어야 한다. 밥-B는 깊이 이상으로 기존 재생 입력이 없어 확보 실패로 포함했다. 나머지 10건은 기존 사용자 검토 영역·최대 10프레임 깊이 입력으로 재생했다. 옛 촬영에는 특징점이 없어 AI 대체를 끈 경로는 높이 확보에 한계가 있다. 밀도는 음식명에 대응하는 고정 식품군(밥 0.73, 쿠키 0.42, 견과 0.63g/mL)이며 DB 연결 오류 평가가 아니다.

현재 소스에는 데모용 필터 변경도 있으므로 `source-hashes.json`으로 실행 버전을 고정하였다. 이 결과를 과거 설치 APK의 동일 재현이나 전체 통합 서비스 정확도라고 보고하지 않는다.

조건별 MAE(g), 상대오차 중앙값, 전체 결과 확보율, 반복 편차, 음식군별 결과와 처리 시간·토큰을 기록한다. 실패를 오차 0으로 취급하지 않는다. 실제 숫자가 나온 공통 표본 비교도 전체 확보율과 함께 별도로 보고한다.

모델은 이전과 같은 gpt-4o-mini다. 앞선 640×480 고해상도 이미지 요청의 사용량과 출력 제한을 기준으로 66회 약 US$0.15~0.30을 예상한다. 실제 토큰·캐시·응답 길이에 따라 달라진다. 자동 재시도는 없고 기존 응답은 덮어쓰지 않는다. 공식 단가는 입력 100만 토큰당 US$0.15, 출력 US$0.60이다([OpenAI 모델 문서](https://developers.openai.com/api/docs/models/gpt-4o-mini)).

로컬 규칙에 따라 호출 수·예상 비용을 알리고 이번 66회에 대한 별도 명시 승인을 받아 실행했다. 기존 9회 승인을 재사용하지 않았다.
